# Khmer autocomplete keyboard

A lightweight Khmer autocomplete input method for macOS and Windows. The keyboard has the usual **two states, English
and Khmer** (toggled by Ctrl+Option+Space on macOS, Ctrl+Alt+Space on Windows). English is pass-through. In the Khmer
state the engine (mode `Auto`) works out by itself what was typed: Khmerlish ("knhom chong" -> Khmer), English -> Khmer
(`water`, Space gives `ទឹក`), keys of the Khmer (NiDA) layout typed on a US keyboard (`xjJuM` is `ខ្ញុំ`), or Khmer script
from the OS keyboard (complete the word, predict the next, fix typos). The engine still has the four modes `Khmer`,
`Latin`, `English`, `Auto`; the shells use only `Auto`. The demo page offers all four.
A browser prototype (`web/template.html`) is the **reference implementation**; the portable Rust
core (`core/`) is a port of it. When the two disagree, the JS is right, and the difference is reported, not fixed silently.

## The Khmer state: engine mode `Auto` (value 3)
Nothing is remapped by the shells. ASCII lands in the document as typed; the **pending run** is the trailing run of ASCII graphic
characters (no whitespace; broader than `latin_suffix`, because NiDA also uses `[ ] ; ' , . / \ \`` and digits). Text that ends in
Khmer (or a word just accepted) has no run: the Khmer-script path runs, which is what the OS Khmer keyboard needs.
- Reading of a run, each candidate with its own **span** (`replace`, `replace_len_utf16`) and a **`source`** (`khmerlish`, `english`,
  `nida`, `raw`; additive JSON field, absent in the other modes):
  1. Khmerlish: `rom_suggest` on `latin_suffix(run)`.   2. English: `english_suggest` on the same letters.
  3. NiDA: every key of the run through `layout::from_ascii` (capitals and shifted symbols use the Shift level) into a Khmer
     *reading*, then `analyze`. Every token a real vocab word and nothing partial: a hit at **tier 0.6**, word = the whole reading,
     span = the whole run. An unfinished last word gives completions (`Complete` only, no next-word, no typo scan) at **tier 1**.
     A partial that is itself a word counts as finished (the DP prefers the cheap tail for prefixes of longer words). A reading
     that a sentence mark (`។ ! ?`) would split gets no NiDA hit. Digit-only runs never auto-convert.
  4. Raw fallback, only when nothing has tier < 2 (rule guesses are tier 1.8, so they count as a hit): at most `AUTO_KEEP` = 4 weak
     candidates, then two chips: `Kind::Layout` (the NiDA reading) and `Kind::Raw` (the text as typed, English), tier 3.
  Merge: sort by tier, then source (Khmerlish > English > NiDA), then P; one candidate per word; at most 8.
- Keys (`Engine::key_action`): **Space** converts only a confident top (tier < 1: Khmerlish exact, English exact/inflection, NiDA
  full word); prefix / typo / rule guesses are shown but never applied, so unknown English stays as typed. **Enter** takes the top
  only if it is a real candidate of a pending run (a layout / raw list passes through, so Enter stays a newline). **Tab** takes
  the top; over a layout / raw list that is the NiDA reading (an explicit convert request).
- Trade-offs, accepted: NiDA is no longer live per key (letters appear on Space / Tab / click). Khmerlish typo tolerance no longer
  fires on Space (Tab does it). Glossed English words typed in the Khmer state convert (`meeting ` -> ជួប through the `meet` gloss;
  the English state is for plain English), and a short English word that is also a Khmerlish spelling goes to Khmerlish (`i` ->
  អ្វី, not ខ្ញុំ: same tier, Khmerlish first). Punctuation glued to a word (`knhom,`) defeats Khmerlish and NiDA conversion until
  there is a Space. With a real vocabulary some random key sequences will happen to be Khmer words (tier 0.6 will need tuning).
- JS: `NIDA` (const, generated from the Rust table), `nidaRead`, `Engine.nidaSuggest` / `Engine.autoSuggest`, and the DOM-free
  `autoResolve(E, text, completedWord)` / `autoKey(E, text, key, completedWord)` live in the **engine part** of the template (the
  golden generator runs them as they are); the UI part only calls them.

## Input modes and the English glossary
- `data/english.json` maps a Khmer word to comma-separated English glosses. **It is a hand-written draft** (273 of the 277 seed words; `តើ`, `ដ៏`,
  `ជាទេ`, `សុភា` have no gloss) and needs a native speaker's review. With a real vocabulary the glossary must grow with it.
- English matching (`enSuggest` in the JS, `english_suggest` in Rust): tier 0 exact gloss, 0.5 inflection (`eating` -> `eat`, small stemmer),
  1 prefix, 2.1/2.2 typo (token of 4+ letters). Space converts only a tier < 1 match (never a half-typed word); Tab/Enter/click take the top one.
- A token has no spaces, so a multi-word gloss ("good morning") is reachable only by its first word as a prefix suggestion; typing
  "good morning " converts word by word. A phrase mode would need look-behind over several English words.
- English golden vectors use their own PRNG, so adding them left every earlier vector byte-identical.
- Compiled format is v2 (`KHDATA02`: adds the English index). v1 files still load (no English).

## Keyboard layout (NiDA)
- The shells no longer remap keys. The layout is used by the engine in Auto mode to read ASCII typed on a US keyboard
  (`layout::from_ascii`); `kh_layout_map` (physical key -> Khmer, by macOS key code / Windows scan code) stays in the C API and
  `khlayout::map` but no shell calls it. Space is **not** part of the layout: NiDA types a zero-width space, the engine needs a real space.
- The table comes from the XKB `kh` layout (xkeyboard-config, NiDA, Jens Herden 2005). Regenerate with `layout/tools/gen_layout.py`
  (it also emits the US Shift pairs `SHIFTED_US`); don't edit by hand. The JS `NIDA` const must equal `from_ascii` (a test compares them).

## Rules that matter
- **JS is the reference.** `tests/golden/gen.mjs` runs `web/template.html` unmodified (it evals the script up to the unique `UI` anchor
  comment) and records outputs; `core/tests/golden_*.rs` must reproduce them exactly. Change JS first, regenerate, then port.
- Normalization lives in three places that must stay identical: `normalize()` in `data/build_data.py`, in `web/template.html`, and `core/src/norm.rs`.
- The series rule is data: `CONS`, `VOW` in `template.html`, `core/src/tables.rs` in Rust (a golden test compares the two). Both directions
  (`romanize`, `compose`) read the tables. Change the tables, not the functions, when fixing a reading.
- `romKey()` reduces a Latin spelling to a sound key. Any change to it changes every match: rerun all tests.
- Names `CONS`, `VOW`, `SIGN` are taken by the series tables in the JS; the on-screen keyboard uses `KB_CONS`, `KB_VOW`, `KB_SIGN`.
- Do not splice the template by searching for comment text like `/* samples */`; use unique anchors.
- Khmer needs a Khmer font to judge rendering. Check visually in a real browser, not only in headless tests.
- Shells (Swift, Rust TSF) are thin: keystrokes and text-before-caret in, candidates out, insert the chosen text. No language logic there.
  The Space/Enter/Tab rules live in `Engine::key_action`. The shells have two states, English (pure pass-through, no engine calls)
  and Khmer (engine mode `Auto`, keys never remapped, Space/Enter/Tab always asked).
- No network calls, no logging of typed text, suggestions off in password / secure-input fields (shell responsibility).

## Decisions (Phases 2-4)
- **macOS:** `KhBridge` is the only code that touches the C API; the controller never sees JSON. Candidates are shown with `IMKCandidates` without
  marked text (unverified on a real Mac, with a documented fallback). Text is inserted with `insertText(replacementRange:)` using the engine's
  `replace_len_utf16`; "just accepted" is dropped on any key and when the caret moves. Off in secure input, in listed apps, and without `khdata.bin`.
  Two states (`Settings.State`: `.khmer` = `InputMode.auto`, `.english` = off); the old three stored modes are dropped (all become Khmer).
- **Windows:** the DLL is a thin client. Deadlines and a circuit breaker bound the damage of a dead engine; failures fail open. The text service
  is registered as a keyboard TIP without the secure-mode category, so Windows disables it in password fields. MSI, not MSIX (COM in HKLM, in-proc injection).
  Two states (`logic::Mode`: Khmer = engine mode 3, English = off); `Plan::Type` and the layout table are gone from the DLL; the registry
  value `State` replaces `Mode` (an old `Mode` value is deleted on load, which makes it Khmer).
  Every Windows API type was checked against `windows` 0.62.2 for x64, x86 and arm64; checking x86 found a real `SetWindowLongPtrW` width bug.
- **Phase 4:** `Scorer` is the seam; `neural` (off by default) holds an async re-rank pipeline (`AsyncRefiner`: submit never blocks, a newer request
  supersedes older ones, results blend with the n-gram scores instead of replacing them). No ONNX dependency yet. `models/manifest.schema.json` +
  `khcore::manifest` define the model file format. `khcore::userdict` is the (unimplemented) opt-in on-device learning interface.
- `core::api_json` shapes the JSON for the C API, WASM and the Windows pipe, so the three cannot drift apart.

## Decisions (Phase 1)
- C ABI v1 (`KH_ABI_VERSION`): opaque `KhEngine*`; `kh_engine_open` / `_open_compiled` / `_open_compiled_bytes` / `kh_engine_free`; `kh_suggest`,
  `kh_key_action`, `kh_string_free`, `kh_last_error`. Every function returns NULL on failure with a per-thread message; panics are caught at the
  boundary; an engine is immutable, so any number of threads may share one. UTF-8 in; `replace_len_utf16` counts UTF-16 units of the text sent.
  Results carry `gain` (key presses saved) next to the candidate fields. The only `unsafe` in the project lives in `capi/src/lib.rs`.
- The WASM wrapper returns JSON strings (no serde-wasm-bindgen). Besides the public API (`suggest`, `keyAction`) it exposes the lower-level
  `analyze`, `khmerCandidates`, `latinCandidates`, `compose` that the demo UI needs; `normalize`, `romKey`, `romanize` are free functions.
- The web demo keeps the JS engine as default. `window.KH_MAKE_ENGINE` (set by `index-wasm.html`) swaps in the Rust engine. The engine part of
  template.html (what the golden generator evaluates) is untouched; only the UI section changed (engine factory, an "Engine:" label).
- The plain `build_demo.py` run deletes `web/index-wasm.html`, so a stale WASM page can never pass the tests.
- WASM size profile `wasm` (opt-level s, LTO, panic=abort): about 680 KB without wasm-opt.
- Probabilities: native tests allow 1e-12; the wasm test requires bit-identical doubles (it passes, 0 inexact). `Candidate.prob` is f32, so a
  consumer must compare it as f32 (`Math.fround`) against a double.

## Decisions (Phase 0)
- `icu_segmenter` is **not used**: `clusters()` is a regex-defined unit (coeng + consonant), not UAX #29, and word segmentation is the specified DP.
  Revisit behind an optional feature for corpus tooling.
- The compiled file is read into memory (safe code only). An `mmap` feature would need one `unsafe`; not added yet (50 MB budget is met without it).
- `fst` for the word index (word -> id, prefix ranges), `unicode-normalization` for NFC/NFD, `serde`/`serde_json` for data.json. No `libm`:
  `core/src/fdlibm.rs` is a port of fdlibm's `log`, the algorithm behind V8's `Math.log`. `libm::log` and the system libm differ from V8 in the
  last bit on ~0.3% of inputs, which could flip a segmentation tie; the golden test checks 25k values bit for bit.
- Scores are f64 inside (like JS), `Candidate.prob` is f32 at the edge. Candidates are built only for the survivors of the top-8 cut.
- `Candidate.replace_len_utf16` is measured in the **raw** text the shell sent (normalization may drop/reorder characters), so a shell can
  use it directly as the replacement range.
- Compiled format `khdata.bin` v1 (`KHDATA01`, little endian): meta JSON, words, freq, bigram CSR, Latin sound index, display spellings, fst.
  Loading validates structure and the fst checksum, so a corrupted file is an `Err`, never a panic (fuzz-tested).

- **Auto:** `Cand` carries `span` (the text it replaces; `shape()` turns it into `replace` / `replace_len_utf16` with `raw_suffix_len_utf16`) and
  `source`. `khmer_suggest_with(.., complete_only)` is the JS `suggest(ctx, limit, completeOnly)`: NiDA completions skip the next-word
  and typo-scan parts, so English typed in the Khmer state costs no 20,000-word scan. Golden vectors for Auto (`nida`, `auto`,
  `flowsAuto`) use their own PRNG, so every older vector is byte-identical.
- C ABI stays v1: `KH_MODE_AUTO = 3` is a new value only. The WASM wrapper gets `autoCandidates` and `nidaRead`; `wasm-adapter.js` exposes `autoSuggest`.

## JS behaviors the port reproduces on purpose (differences from the written spec)
1. `romKey` maps `ə ɛ ɨ ɔ ɑ` before lowercasing, so uppercase `Ə Ɛ Ɔ` are deleted, not mapped.
2. Empty partial: `next` and `common` candidates are sorted together by P (a common word can outrank a next word).
3. Segmentation caps a known word at `min(24, longest vocab word)` clusters.
4. Latin typo tier compares the token key with the entry key and with the entry key cut to the token key's length.
5. Runs are split with JS `\s` (includes U+FEFF and U+00A0, excludes U+0085).
6. `romanize`: the `"m"` branch for nikahit after vowels other than ា/ុ is dead code in JS, so e.g. `កើំ` reads "kaeu". Ported as is. Open question for the owner.
7. Tab accepts the top candidate in both modes.
8. The JS rewrites all text before the caret on accept; an IME cannot, so the engine only replaces the pending token / partial.
9. Latin mode with no pending token falls back to Khmer-script suggestions (JS `refresh()`).
10. Auto: Space ignores `completed` (the `input` event clears it); Enter and Tab honour it. A word just accepted ends the run.
11. Auto sorts with `a.tier - b.tier || source rank || (b.p || 0) - (a.p || 0)` on a stable sort; `p` of a layout / raw chip is null and counts as 0.
12. Auto: the NiDA hit's P is P(last token | the token before it, or the word before the run); `w` is the last token's id.
13. Auto and un-normalized text: the run is read from `normalize(text)`, so zero-width characters inside ASCII are dropped; the
    replace length is measured in the raw text (`raw_suffix_len_utf16`), unlike Latin mode, which uses the normalized token length.

## Known limits
- Built-in data is tiny (277 words). Real coverage needs the Wikipedia build.
- Rule-made spellings (`compose()`) are guesses: Khmer spelling is not fully phonetic.
- Lexicon spellings are the author's, not collected from real users. Grow them from real chat text.
- Typo scans cover only the 20,000 most frequent words (as in the JS).
- The English glossary is tiny and unreviewed; multi-word glosses are only reachable by their first word.
- Auto's tier thresholds (0.6 for a NiDA hit, the Space-confidence rules, `AUTO_KEEP`) are judgement calls to tune on real typing.
- Unix-socket / named-pipe latency was not measured on Windows. The engine itself meets its budgets (see core/tests/perf.rs).
